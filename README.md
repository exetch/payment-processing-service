# Payment Processing Service

Асинхронный микросервис процессинга платежей: принимает запрос на оплату,
проводит его через эмулятор платёжного шлюза и уведомляет клиента вебхуком.

**Стек:** FastAPI, Pydantic v2, SQLAlchemy 2.0 (async), PostgreSQL, RabbitMQ
(FastStream), Alembic, Docker Compose.

**Гарантии:** Transactional Outbox, идемпотентность API и consumer'а, retry
с экспоненциальной задержкой, Dead Letter Queue, подписанные вебхуки.

## Архитектура

```
        POST /api/v1/payments                       ┌────────────────────┐
client ───────────────────────▶ API (FastAPI)       │  эмулятор шлюза    │
        202 {payment_id}        │                   │  2-5 c, 90/10      │
                                │ одна транзакция:  └─────────▲──────────┘
                                │ payments + outbox           │
                                ▼                             │
                          PostgreSQL ◀──────────── consumer (FastStream)
                                ▲                   │ 1. эмуляция шлюза
                  poll, SKIP LOCKED                 │ 2. статус в БД
                                │                   │ 3. webhook клиенту
                          outbox relay              │    (ретраи → DLQ)
                                │ publish           ▼
                                ▼              webhook_url клиента
                          RabbitMQ (payments.new)
```

- **API** пишет платёж и outbox-событие в одной транзакции, поэтому событие не
  теряется даже при недоступном брокере.
- **Outbox relay** (фоновая задача API-процесса) забирает события по одному под
  `FOR UPDATE SKIP LOCKED`, каждое в своей транзакции. `published_at` проставляется
  только после успешной публикации: гарантия at-least-once, дубликаты гасит consumer.
- **Consumer** (один обработчик) эмулирует шлюз, обновляет статус, доставляет
  вебхук. Шаги идемпотентны, поэтому редоставка безопасна.

### Топология RabbitMQ

```
exchange payments        (direct) ──payments.new──────▶ queue payments.new (DLX ▶ payments.dlx)
exchange payments.retry  (direct) ──<имя очереди>─────▶ payments.new.retry.1   TTL 2s ┐
                                                        payments.new.retry.2   TTL 4s ├─ DLX ▶ payments
                                                        payments.new.retry.3   TTL 8s ┘  (rk payments.new)
exchange payments.dlx    (direct) ──payments.new──────▶ queue payments.new.dlq
```

Retry-очереди без подписчиков: сообщение отлёживает TTL и возвращается в
`payments.new` средствами брокера. TTL задан на очередь, а не на сообщение, иначе
истёкшее сообщение ждало бы впереди стоящего (head-of-line blocking).

## Быстрый старт

Нужен Docker с Compose v2, настройка не требуется:

```bash
docker compose up -d --build
docker compose run --rm api alembic upgrade head
```

Поднимаются `postgres`, `rabbitmq`, `api` (http://localhost:8000, Swagger `/docs`),
`consumer` и `webhook-sink` (демо-приёмник вебхуков). Вторая команда применяет
миграции; до неё эндпоинты платежей отвечают ошибкой.

Конфигурация задаётся переменными окружения или `.env`, см. [.env.example](.env.example):

| Переменная | Дефолт | Смысл |
|---|---|---|
| `API_KEY` | `supersecret-dev-key` | ключ заголовка `X-API-Key` |
| `DATABASE_URL` | `postgresql+asyncpg://payments:payments@postgres:5432/payments` | подключение к БД |
| `RABBITMQ_URL` | `amqp://guest:guest@rabbitmq:5672/` | подключение к брокеру |
| `GATEWAY_MIN/MAX_DELAY_SECONDS` | `2` / `5` | задержка эмулятора шлюза |
| `GATEWAY_SUCCESS_RATE` | `0.9` | доля успешных платежей |
| `WEBHOOK_TIMEOUT_SECONDS` | `5` | таймаут доставки вебхука |
| `WEBHOOK_SIGNING_SECRET` | `dev-webhook-signing-secret` | секрет подписи вебхуков |
| `WEBHOOK_ALLOWED_HOSTS` | `webhook-sink` в compose | хосты-исключения из защиты от SSRF |
| `CONSUMER_MAX_RETRIES` | `3` | число ретраев после первичной попытки |
| `RETRY_BASE_DELAY_SECONDS` | `2` | база экспоненты: 2s, 4s, 8s |
| `OUTBOX_POLL_INTERVAL_SECONDS` | `0.5` | период опроса outbox |
| `OUTBOX_BATCH_SIZE` | `100` | сколько событий relay берёт за проход |
| `OUTBOX_RETRY_BASE/MAX_DELAY_SECONDS` | `1` / `60` | backoff для неопубликованной строки |

## API

Эндпоинты `/api/v1/*` требуют заголовок `X-API-Key`. Документация: `/docs`.

### POST /api/v1/payments

Заголовок `Idempotency-Key` обязателен. Ответ `202 Accepted`, результат придёт
на `webhook_url`.

```bash
curl -s -X POST http://localhost:8000/api/v1/payments \
  -H "X-API-Key: supersecret-dev-key" \
  -H "Idempotency-Key: order-42-attempt-1" \
  -H "Content-Type: application/json" \
  -d '{
        "amount": "1499.90",
        "currency": "RUB",
        "description": "Заказ #42",
        "metadata": {"order_id": 42, "customer": "ivan"},
        "webhook_url": "http://webhook-sink:9000/webhook"
      }'
```

```json
{"payment_id": "08f6e893-ef27-4341-aa0f-7fef984f963e", "status": "pending", "created_at": "2026-08-05T16:30:04.073448Z"}
```

Повтор с тем же ключом и телом возвращает `202` с исходным `payment_id` без новых
записей. Тот же ключ с другим телом даёт `409`.

Суммы передаются и возвращаются строкой: для денег плавающая точка не годится.
Валюты: `RUB`, `USD`, `EUR`.

### GET /api/v1/payments/{payment_id}

```json
{
  "payment_id": "08f6e893-ef27-4341-aa0f-7fef984f963e",
  "amount": "1499.90",
  "currency": "RUB",
  "description": "Заказ #42",
  "metadata": {"customer": "ivan", "order_id": 42},
  "status": "succeeded",
  "webhook_url": "http://webhook-sink:9000/webhook",
  "created_at": "2026-08-05T16:30:04.073448Z",
  "processed_at": "2026-08-05T16:30:06.959970Z",
  "webhook_delivered_at": "2026-08-05T16:30:06.978740Z"
}
```

Коды ошибок: `401` (ключ), `404` (не найден), `409` (конфликт идемпотентности),
`422` (валидация, включая отсутствие `Idempotency-Key`, запрещённый или слишком
длинный `webhook_url`), `500` (непредвиденный сбой). Все ответы, включая `500`,
приходят в одном формате `{"detail": ...}`; текст исключения наружу не уходит,
он попадает в структурный лог вместе с методом и путём запроса.

## Вебхук

Отправляется в обоих исходах, `succeeded` и `failed`:

```json
{
  "event_id": "0f2b1c4e-8a3d-4c21-9f77-1d5b6a0e2c34",
  "event": "payment.processed",
  "api_version": "2026-08-05",
  "payment_id": "08f6e893-ef27-4341-aa0f-7fef984f963e",
  "status": "succeeded",
  "amount": "1499.90",
  "currency": "RUB",
  "description": "Заказ #42",
  "metadata": {"customer": "ivan", "order_id": 42},
  "processed_at": "2026-08-05T16:30:06.959970Z"
}
```

**Контракт получателя.** Отвечайте любым `2xx` до бизнес-логики, таймаут 5 секунд;
редирект успехом не считается. Доставка at-least-once, дедуплицируйте по `event_id`
(он одинаков для всех попыток одного события). Порядок доставки не гарантирован.
Формат версионируется полем `api_version`.

**Подпись.** Заголовок `X-Webhook-Signature: t=<unix>,v1=<hmac_sha256>`.
Подписывается строка `<t>.<сырое тело>` секретом `WEBHOOK_SIGNING_SECRET`.
Timestamp входит в подпись, поэтому отвергайте метки старше 5 минут: это защита от
переигрывания перехваченного уведомления. Сравнивайте подписи за константное время.
Пример проверки: [scripts/webhook_receiver.py](scripts/webhook_receiver.py),
результат виден в логах демо-приёмника полем `signature`.

**Куда можно слать.** Адрес проверяется дважды. IP-литерал из приватных, loopback
и служебных диапазонов отсекается на входе API (`422`). Перед отправкой хост
резолвится и проверяются реальные адреса, что закрывает SSRF через домен,
указывающий внутрь сети или на `169.254.169.254`. Запрещённый адрес считается
постоянным отказом: сообщение уходит в DLQ без ретраев. Исключения точечные, через
`WEBHOOK_ALLOWED_HOSTS`; в compose там только `webhook-sink`, остальные приватные
адреса запрещены и в демо.

Логи приёмника: `docker compose logs -f webhook-sink`. Для приёмника на хосте
используйте `http://host.docker.internal:<port>/...`.

## Надёжность

### Retry и DLQ

Первичная попытка плюс до `CONSUMER_MAX_RETRIES` ретраев с задержками 2s, 4s, 8s.
Ретраится сбой обработки: ошибка БД, сетевая ошибка, не-2xx от получателя. Номер
попытки едет в `x-attempt`, последняя ошибка в `x-last-error`.

После исчерпания попыток сообщение публикуется в `payments.dlx` с исходным payload
и диагностикой (`x-attempt`, `x-dlq-reason`), оседая в `payments.new.dlq`. Статус
платежа не меняется: типичный случай, когда платёж терминальный, а
`webhook_delivered_at` пуст.

`failed` от шлюза (те самые 10%) это бизнес-результат, а не сбой: статус
терминальный, вебхук отправляется, ретраев нет. Так же для запрещённого адреса
доставки и отсутствующего платежа: постоянный отказ уходит в DLQ сразу.

Закрыты четыре способа потерять сообщение молча:

- **Отбраковка до обработчика.** Невалидный payload FastStream отвергает раньше
  вызова хендлера, поэтому у `payments.new` объявлен собственный DLX: брокер уводит
  такое сообщение в DLQ с `x-death.reason: rejected`.
- **Нечитаемое тело.** JSON парсится до открытия acknowledgement-скоупа, где
  исключение оставило бы сообщение вечно unacked. Кастомный декодер возвращает
  заглушку, её отбраковывает валидация уже внутри скоупа.
- **Недоставленная публикация.** Публикация идёт с `mandatory=True` и
  `on_return_raises=True`: если маршрутизировать некуда, `publish` бросает
  исключение и событие остаётся неопубликованным. Строка получает `attempts`,
  `last_error` и `next_attempt_at` с экспоненциальным backoff, поэтому она не
  занимает голову очереди: relay сразу идёт к следующим событиям. Каждое событие
  живёт в своей транзакции, так что сбой одного не откатывает уже опубликованные
  и не порождает шторм дублей.
- **Сбой republish.** Сообщение не возвращается в очередь с прежним `x-attempt`,
  иначе получился бы бесконечный цикл. Оно отвергается, и в DLQ его уводит брокер.

Проверить негативный путь: создайте платёж с `webhook_url` на недоступный хост,
через ~20 секунд сообщение появится в `payments.new.dlq`. Очереди видны в
management UI: http://localhost:15672 (guest/guest).

### Идемпотентность

1. **API.** `UNIQUE(idempotency_key)`. Повтор возвращает исходный платёж, гонка
   одновременных запросов разрешается перехватом нарушения уникальности.
2. **Consumer.** Статус меняется guard-update'ом только из `pending`, повторный
   вебхук не отправляется.

Граница гарантии проходит по состоянию в БД и вебхуку. Вызов шлюза выполняется до
фиксации статуса, поэтому падение в этом окне даст повторное обращение к шлюзу.
Реальному гейтвею нужно передавать idempotency-key в его API.

### Пробы состояния

`GET /healthz` это liveness, процесс жив. `GET /readyz` это readiness: проверяет
БД (`SELECT 1`), брокер (`ping`) и состояние relay, отдаёт `503` с разбивкой по
проверкам. Используется как healthcheck сервиса `api`. За relay следит колбэк,
пишущий `CRITICAL` при его смерти.

```bash
python -m venv .venv && .venv/Scripts/activate      # Windows; на *nix bin/activate
pip install -r requirements-dev.txt
ruff check app tests && mypy app
pytest -q                                           # нужен Docker

```

### Тесты

176 тестов, около 77 секунд. Запущенный compose не нужен: Postgres и RabbitMQ
поднимает сам pytest через testcontainers, схему накатывает Alembic.

- `tests/unit`: конфигурация, сравнение ключа, JSON-логи, эмулятор шлюза, схемы,
  сверка тела при повторе ключа, подпись вебхука, проверки адреса. Без инфраструктуры.
- `tests/integration`: контракт API включая гонку по одному ключу и формат ошибок,
  транзакционность outbox, relay, обработчик, ретраи и DLQ, ограничения БД, пробы.

Покрыты негативные сценарии: недоставленная публикация не помечает событие
отправленным, редоставка не списывает дважды и не дублирует вебхук, сбой republish
уводит в DLQ, оба вида нечитаемых сообщений оседают в DLQ. Эмуляция шлюза в тестах
детерминирована, случайность исключена.

CI ([.github/workflows/ci.yml](.github/workflows/ci.yml)): линтеры, тесты и
проверка миграций (`upgrade head`, `check` на дрейф, `downgrade base`, повторный
`upgrade`).

Два нюанса. После `downgrade` и `upgrade` под работающим сервисом нужен рестарт
`api` и `consumer`: пул asyncpg кеширует OID пересозданных enum-типов. RabbitMQ не
разрешает менять аргументы существующей очереди, поэтому при правке топологии на
живом брокере сервис остановится с внятной ошибкой, очереди нужно пересоздать
(`docker compose up -d --force-recreate rabbitmq`).

## Границы решения

**Трактовки ТЗ.** «3 попытки» это одна первичная плюс три ретрая, затем DLQ.
Повтор ключа с тем же телом даёт `202` с исходным платежом, с другим `409`.
Отказ шлюза это бизнес-результат `failed`, а не повод для ретраев.

**Осознанные упрощения.**

- Окно ретраев вебхука секунды, а не сутки: у Stripe до 3 дней, у ЮKassa 24 часа.
  Здесь 2s/4s/8s, чтобы демонстрация не шла три дня; значения в конфиге.
- Ключи идемпотентности живут вечно. TTL (у Stripe 24 часа) потребовал бы
  отдельной таблицы `idempotency_keys` с `expires_at` и чисткой.
- Ответ не сохраняется, а пересобирается: повторный `POST` вернёт актуальный
  статус, а не байт-в-байт первый ответ. Замораживать `pending` навсегда хуже.
- Ключ идемпотентности не разделён по клиентам: API-ключ один. При
  мультитенантности ключ станет составным `(client_id, idempotency_key)`.
- Outbox не чистится. В проде нужен ретеншн: удалять строки, когда терминальны
  и платёж, и его вебхук.
- У строки, которую не удаётся опубликовать, нет предельного числа попыток: она
  откладывается всё дальше (до `OUTBOX_RETRY_MAX_DELAY_SECONDS`), но не переходит
  в терминальное состояние. В проде к ней нужен либо флаг `blocked` с алертом,
  либо отдельная outbox-DLQ.
- Relay живёт в процессе API. `SKIP LOCKED` делает реплики безопасными, но при
  масштабировании его стоит вынести отдельным сервисом.
- Нет rate limiting, метрик и трейсинга. В проде: ограничитель на `POST`, лаг и
  глубина outbox, сквозной correlation-id.
- Контейнеры работают от root, зависимости заданы диапазонами без lock-файла.
- DLQ разбирается руками: сообщение возвращается в `payments.new` через
  management UI, обработка идемпотентна.
